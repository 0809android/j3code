# 端末の紹介（P1.5）

仕様 v3.5 の §18.2 の 3〜5 の実装です。承認済みの端末（紹介元）が、新しい端末を、紹介元がつながっているすべてのホストへ、確認コードの見比べ 1 回で追加します。リレーには、手を加えていません（既存のペアリングの窓を使います）。

## 登場するもの

| 名前            | 説明                                                                                                 |
| --------------- | ---------------------------------------------------------------------------------------------------- |
| 紹介元（A）     | 承認済みで、ホストが `devices:invite` を付けた端末。ホストごとに別の `Dk`（`Dk_A,i`）を持つ          |
| 新しい端末（N） | 紹介される端末。ホストごとに、新しい `Dk_N,i` を作る（ホストどうしを、リレーに結びつけさせないため） |
| `S`             | A が作る 128 ビットの使い捨ての秘密。QR の `#` の後ろにだけ入る。A は、各ホストに E2E の内側で渡す   |
| 紹介の窓        | ホストごとに同時 1 つ、5 分。開いている間、ホストはリレーのペアリングの窓を開ける                    |

## 流れ

1. A が「端末を紹介」を押す。A は `S` を作り、各ホストに、自分の E2E のトンネルの内側で `POST /api/relay/introduction {secret}` を送る。ホストは、A が台帳で有効で、`devices:invite` を持ち、1 日の上限（3）に達していないときだけ、紹介の窓を開き、`introductionId`（16 バイトの乱数）と期限を返す。
2. A は、窓を開けたホストだけを並べた QR を出す: `k3relay://introduce?v=1&exp=…&h=<Hk>,<relayUrl>&h=…#s=<S>`。ホストの一覧は、QR（対面）でだけ渡り、リレーは見ない。hostId は `Hk` から計算する。
3. N が QR を読む。ホストごとに `Dk_N,i` を作り、`peers = [(hostId_i, alg_i, Dk_N,i)]`（hostId の昇順）を決める。N は、確認コード `code = 40bit(sha256(lp("k3relay-v1/introduction-code") ‖ lp(S) ‖ lp(hostId_1) ‖ lp(alg_1) ‖ lp(Dk_1) ‖ …))` を出す。
4. N は、各ホストに、`Hk` をピン留めした匿名の E2E（既存の `?pairing=1`）を張り、`introduction-claim {alg, dk, name, peers, keyProof, proof}` を送る。
   - `proof = HMAC(S, "k3intro" ‖ th ‖ alg ‖ Dk ‖ name ‖ peers)`（QR を見た者だけが出せる）
   - `keyProof = sign_Dk("k3code-e2ee-v2/intro" ‖ th ‖ alg ‖ Dk)`（`Dk` の所有。このセッションに結びつく）
   - ホストは、`peers` に自分の hostId と、この `Dk` が入っていることを確かめる。`S` は、正しい claim でだけ使い切る。無効な claim は数え、10 回で窓を閉じる。
5. A は、各ホストに `POST /api/relay/introduction/claim` で、届いた claim（端末名、`Dk`、`peers`）を受け取る。**全ホストの `peers` が同じで、各ホストの `Dk` がその中の自分の行と一致すること**を確かめ、`S` と `peers` から同じ式で `code` を出す。ユーザーは、A と N の画面のコードを見比べて、A で承認する。
6. A は、ホストごとに、そのホストでの自分の `Dk_A,i` で署名し、`POST /api/relay/introduction/approve` を送る。

```
sig = sign_DkA,i(relaySigningInput("k3relay-v1/introduction-approval",
        hostId, introductionId, 紹介元の deviceId, 新しい端末の deviceId, alg, Dk, 端末名, code, 期限))
```

7. ホストは、次をすべて満たすときだけ承認し、N の待っている匿名セッションに grant と bootstrap 資格情報を返す:
   - 送ってきたトンネルの端末（E2E で認証済み）が、窓を開けた紹介元と同じ
   - 紹介元が、**今も**台帳で有効で、`devices:invite` を持つ（失効した紹介元の署名は無効）
   - `introductionId` が今の窓のもので、未使用（承認・拒否・期限切れで消える。再利用は効かない）
   - 期限（窓を開けてから 5 分）の前
   - 署名が、紹介元の台帳の `Dk` で検証できる（別ホスト・別の新端末・別の名前・別のコードへの流用は、署名の入力が変わるので失敗）
   - `code` が、ホストが `S` と claim の `peers` から計算したものと一致（見比べたコードに結びつく）

## 台帳に残すもの

端末ごとに、承認の経路 `approvedVia`（`host` / `qr` / `account` / `introduction`）と、紹介なら紹介元の `introducedBy`（deviceId）、権限 `permissions`（今は `devices:invite` だけ）を記録します。「ホストの承認が最終」は、**ホストの台帳に記録された承認**という意味です。ホストの画面での承認と、権限を持つ端末による紹介の、どちらもここに残ります。

- 新しく台帳に入る端末は、どの経路でも `permissions` が空です。`devices:invite` は、ホストの画面（所有者のスコープ `relay:configure`）でだけ付け外しできます。**紹介された端末は紹介できません（連鎖しない）。**
- 紹介された端末の権限（スコープ）は、QR でペアリングした端末と同じ通常の端末のもの（`relay-paired-device`）です。紹介元が、所有者の権限を付けることはできません。

## 失効

- ホストの画面から、どの端末も失効できます。
- `devices:invite` を持つ端末は、自分のトンネルの内側（`POST /api/relay/devices/revoke`）で、**`devices:invite` を持たない**ほかの端末を失効できます（失くした端末のため）。自分自身と、ほかの紹介元は失効できません。ホストの所有者のセッションは台帳の端末ではないので、この経路では触れません。

## 上限と通知

- 1 ホストあたり、紹介での承認は 24 時間で 3 台まで（台帳の `approvedVia: introduction` と承認日から数えるので、再起動しても戻らない）。窓を開ける回数も、24 時間で 10 回まで（メモリ）。
- 紹介で承認したら、ホストは、通知の鍵を登録したすべての有効な端末に、種類 `device` の通知を送ります（端末ごとの設定によらず届く、安全のための通知）。ホストの画面には、端末の一覧に「紹介で追加（紹介元: …）」が出ます。

## 選ばなかった案

- **N が全ホストで 1 つの `Dk` を使う:** コードは簡単になるが、リレーが、同じ端末が複数のホストを使うことを知る（既存の「ペアリングごとに別の鍵」を崩す）。`peers` をコードに入れることで、鍵を分けたまま、見比べを 1 回にした。
- **ホストの一覧を、リレー経由で A から受け取る:** A と N の間に、リレーを通る別のチャネルが要る。QR に入れれば、リレーは一覧を見ない（ホスト 8 台まで）。
- **署名なしで、A のトンネルの認証だけで承認する:** 台帳に、何を承認したかの証拠が残らない。署名には、ホスト、窓、両方の端末、端末名、コード、期限を入れる。
