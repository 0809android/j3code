# K3 Relay の透明性: 何が見えて、何が見えないか

K3 Relay は、外から家のマシン（K3 のホスト）につなぐための、中継サーバーです。ここでは、リレーが何を見て、何を残し、運営が何を見られるかを、できるだけ正直に説明します。

## 要点

- リレーを通る通信は、**ホストと端末の間で暗号化されています（E2E）**。リレーは暗号文を右から左へ渡すだけで、中身は読めません。
- リレーは、**あなたの名前、端末の名前、プロジェクトの名前、IP アドレスを、保存しません。**
- 保存するのは、ホストと端末の**公開鍵のハッシュ**、許可の記録、月ごとの転送量などだけです。全部の一覧は [DATA.md](./DATA.md) にあり、コードから自動で作られます。
- **接続のメタデータ**（いつ、どのくらいつながっていたか）は、仕組みの上、運営が見ようと思えば見られます。ログに残さない設定にしていますが、それは約束であって、外から証明できるものではありません。下の「運営が見られるもの」を読んでください。
- コードはすべて公開されています。ビルドの出所も公開され、自分で再ビルドして照合できます（[VERIFY.md](./VERIFY.md)）。気になる人は、**自分でリレーを動かせます**。

## リレーに見えるもの、見えないもの

| 見えるか | 内容                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------ |
| 見える   | ホストの ID（公開鍵のハッシュ）と、端末の ID（同じく公開鍵のハッシュ）。誰のものかは分かりません |
| 見える   | あるホストに、あるタイミングで、端末がつないだこと、つないでいる間の通信量                       |
| 見える   | 接続元の IP アドレス（つなぐ瞬間に、通信の仕組みの上で必ず届きます。保存はしません）             |
| 見えない | 通信の中身（コマンド、会話、ファイル、画面）。暗号文のままです                                   |
| 見えない | 端末の名前、ホストの名前、プロジェクトやスレッドの名前、アカウント、メールアドレス               |
| 見えない | 通知の中身（通知を足すときも、暗号文のまま届けるだけです）                                       |

リレーは、「登録済みのホストと、そのホストが許可した端末」の間だけをつなぎます。誰でも使えるプロキシにはなりません。

## 保存するもの、しないもの

保存するもの（SQLite に書きます）:

- **ホスト**: ホストの ID、公開鍵、登録した日と最後に接続した日（日付だけ。時刻は残しません）。365 日つながらなければ消えます。
- **許可**: 端末の ID、公開鍵、ホストが署名した許可証と期限。名前や権限は入れられません。期限や失効から 30 日で消えます。
- **失効の記録**: 30 日で消えます。
- **月ごとの転送量**: ホストごとの、その月の合計バイト数。2 か月で消えます。
- **招待コードのハッシュ**: セルフホストで招待制にしたときだけ使います。

保存しないもの: 通信内容、通知の中身、端末名、ホスト名、プロジェクト名、スレッド名、IP アドレス。

メモリにだけ置いて、再起動で消えるもの: 認証の使い捨ての値、いまのセッション、IP ごとの接続回数（乱用を止めるため）、指標。

列の一つ一つは、[DATA.md](./DATA.md) で確かめられます。DB に、IP や名前のための列を足すと、テストが失敗するようになっています。保存するものを増やすときは、DATA.md の差分が、必ず公開の履歴に残ります。

## 運営が見られるもの

リレーのプログラム自体は、アクセスログを書きません。ですが、運営が「何も見られない」わけではありません。正直に書きます。

**リレーの手前にある Caddy（TLS を受ける部分）と、サーバーの OS、OCI のネットワークは、接続のメタデータを見られる位置にいます。**

- 接続元の IP アドレス、接続した時刻、通信量、つないだ先の URL（`/v1/client/<ホストの ID>` のような形）は、暗号化された通信（TLS）の入り口で、いったん平文になります。ここまでは、ホストと端末の E2E の外側です。
- つまり運営は、仕組みの上、「どの IP から、どのホストの ID に、いつ、どのくらいつながったか」を観測できます。ホストの ID は公開鍵のハッシュなので、人の名前には結びつきませんが、IP と組み合わせれば、同じ人の接続だと推測できることがあります。
- 通信の**中身**は、ここでも読めません。

Caddy のログの扱い（公開されている `Caddyfile` と `docker-compose.example.yml` の設定）:

- **アクセスログは出しません**（`log` の指定を書かないと、Caddy はアクセスログを書きません。`src/ops.test.ts` が、これを CI で検査しています）。
- ただし、**エラーログ（ERROR）だけは出ます**。証明書の取得の失敗や、TLS の失敗などのときに、接続元の IP がエラーの行に出ることがあります。
- そのログは、compose の設定で、**1 MiB の 1 ファイルを使い回す**ので、古いものから消えていきます（長く残りません）。
- 残したくない人は、セルフホストなら `logging: driver: none` にできます。

リレーのプログラムは、`listening`、`purged`、`closed` と、例外の種類の行だけを書きます。パス、メソッド、ホストの ID、IP は書きません。

そのほか、OCI（サーバーを借りているクラウド）が、仮想マシンの外側で、ネットワークの量やメタデータを記録している可能性があります。それは、運営の手の届かないところです。

## どこまで信じなくてよいか

- **通信の中身**は、運営を信じなくても、守られます。リレーが書き換えられていても、暗号文しか見えず、端末やホストのなりすましは、署名と E2E の確認で失敗します。
- **「保存しない」と言っていること**は、コードを読んで、確かめられます。ただし、**いま動いているサーバーが、公開コードと同じものだと、外から証明する方法はありません**（[VERIFY.md](./VERIFY.md) の「限界」）。公開コードのビルドの出所と、再ビルドでの照合までは、第三者が確かめられます。
- **接続のメタデータ**は、守りたいなら、自分でリレーを動かすのが確実です。あるいは、リレーを使わず、LAN、Tailscale、WireGuard、SSH の直結を使えば、リレーには何も届きません。

## 自分で動かす

リレーの URL は、K3 の設定で差し替えられます。`infra/k3-relay/` に Dockerfile、compose の例、Caddyfile、手順（[README](../README.md)）があります。自分のリレーなら、ログの扱いも、保存の期間も、自分で決められます。
